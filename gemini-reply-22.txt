1 本轮问题：锻造的第一步走错了顺序
1.1 一句话问题
原 V1 管线是「缺口检测 → 直接出蓝图 → 试造」。用户指出这个顺序不对：缺口之后应先去各大信源和平台（最好先去 GitHub）找有没有人家已经造好的同类工具，能拿来用的就不要从零造，不重复造轮子。本轮要定的是：这个「先找现成」环节插在哪、怎么找、怎么评、找到之后分几条路走。
1.2 用户原话与叫停背景
「他这个缺口检测了之后，不是直接出蓝图，而是像那个学习回路那样，先去各大信源或者平台，最好的就是直接去 GitHub，先看看有没有类似的工具，有没有人家已经造好的工具，这样子，我们就不用从零造工具，就不用重复造轮胎，懂我意思吗，先把这个思路跟 Gemini4 再聊一聊，再商量一下」——用户，2026-11-18

1.3 为什么这个纠正成立（Muse 的判断）
成本。从零锻造是最贵的一条路：写蓝图、两道监工门、试造、试用期、熔断，一整套成本约 50–150 毫分/个，还要承担坏工具在无沙箱环境里的风险。现成工具若成熟，这些成本大部分可以省掉。
可靠性。现成工具经过真实用户检验，可靠性通常高于 007 用快速模型一夜自造的脚本；自造工具最容易出的问题恰恰是边界情况没人踩过。
一致性。这与学习回路是同一个思想：学习回路本来就规定先查分层信源（官方文档、GitHub 高星项目在内），只是当时那套流程终点是「学成技能」，没有明确「找到现成工具就直接采用」这条出口。本轮是把同一个思想补到锻造入口。
边界。但复用不是无条件优先：许可不合、长期无人维护、依赖过重、来路不明的脚本，在 007 无沙箱、权限全开、同机跑着用户在用服务的环境里，风险可能比自造更大。所以需要评估和分流，而不是「找到就用」。

3.2.1 GitHub 检索怎么做（初步设想，请重点评审）
检索词从缺口报告里提炼：缺口要解决的任务动词 + 对象 + 关键约束（如语言、平台），中英文各一组；007 已有抓取与搜索类工具，检索动作本身不新造工具。

3.3 候选评估维度：八个维度，先过红线再打分
评估分两步：先过第 3.5 节的红线（许可、安全、运行时），任一不过直接淘汰，不打分；过了红线的候选再按八个维度评估，产出候选清单（每个候选一页，附证据链接与日期）。

3.4 四条分支的判定标准（初步门槛，请重点评审）

判定由谁做：初步设想是快速模型（flash）按本节标准产出分流建议，监工在审蓝图（B/C/D 路）或审验证结果（A 路）时连带复核分流是否选对——「明明有现成却去自造」和「明明该自造却硬套现成」都算分流错误，应被打回。分流本身要不要单独设一道监工门，是问题 8 请你判断的事。
3.5 安全与许可红线：这几条不过，评估直接淘汰
许可。许可证缺失或不允许当前使用方式的，不采用、不复制代码；借鉴思路也要在蓝图里写清来源。强传染性许可证的代码不得直接并入 007 本体——具体边界请你在问题 5 里细化。
来路。安装或运行需要执行远程下载的脚本、或来源无法核实的二进制文件的，默认淘汰；确有必要时按高风险处理，人工确认。
凭据。工具若必须接触凭据，必须在蓝图或采用说明里逐项声明接触哪些凭据、发往哪里；未声明即视为红线不过。此条沿用 V1 对自造蓝图的凭据声明要求，对外部工具同样适用。
形态。要求常驻重型服务、独占端口与现有服务冲突、或必须使用 Docker 的，与 007 的部署形态冲突，淘汰或降为 C 路借鉴。
维护与漏洞。已明确停止维护、或存在未修复的高危安全问题且无替代版本的，淘汰。
3.6 成本与上限：检索也要花钱，必须封顶
检索与评估的全部模型调用计入每日 0.50 元进化预算（沿用 V1 口径，打回与重试同样计入），超支按 PAUSED_BUDGET 在步骤边界暂停、次日续跑。
单次缺口的检索设上限（初步值）：候选粗筛 ≤5 个、细看 ≤3 个、检索轮次 ≤2 轮；达到上限仍无合格候选，直接转 D 路，不无限搜下去。数值是否合理见问题 7。
检索的抓取动作优先用 007 已有的搜索/抓取工具完成；模型只负责提炼检索词、粗筛和写评估，不逐页细读全部结果，以控制 token。
一个现实提醒：GitHub 未登录搜索与接口调用有频率限制，夜间窗口里批量检索可能触发限流。是否需要预留令牌、以及限流时是降速续跑还是直接转 D 路，见问题 7。
3.7 与学习回路的关系：共用一套检索，别建两套
学习回路（第 24 步，未开工）的夜学本来就要按分层信源检索：官方文档、GitHub 高星项目、社区动向。本轮的复用检索与夜学是同一种动作的两个出口：夜学找到的是知识，出口是技能草稿；复用检索找到的是成品工具，出口是采用或包装。初步立场是两者共用同一套检索与留痕机制，只在产出物上分流，避免第 25 步之前就出现两个各自维护的搜索子系统。两者是合并成一个模块还是只共用底层抓取，请你在问题 10 里给判断。

4 风险自曝：Muse 先说自家方案的毛病
1. 拿来主义的安全敞口比自造更大。采用的外部工具在真实任务里闯祸时，试用期与熔断是事后止损；若工具本身带恶意或有隐蔽的数据外发行为，staging 的功能测试测不出来。安全审查靠模型读说明和代码，能查到多深，没有实测证据。
2. 许可审查容易做浅。许可证的坑不在仓库首页那一行：子目录、 vendored 代码、示例代码可能各有许可证。只看主许可证就采用，日后公开仓库（007 有公开库）时可能出问题。
3. 依赖膨胀侵蚀单体形态。007 的部署形态是单个 Go 二进制加脚本。外部工具一旦以脚本形态大量引入，tools 目录会变成杂物间：运行时版本、依赖冲突、路径问题都会回来，与当初选 Go 单体的初衷相悖。
4. 检索假阳性与假阴性。按关键词搜同类工具，搜到的往往是「名字像」而非「功能合」。flash 粗筛若只看简介，容易把营销型仓库当成熟工具，或把真正合适的低星仓库筛掉。
5. 上游断裂没有监测。今天活跃的项目明年可能弃坑。采用时省下的自造时间，可能在上游停更、改接口、改许可证时连本带利还回去。V1 已有技能过期机制，但外部工具的「上游变化监测」还没有设计。
6. 评估成本可能反噬预算。每个缺口都先检索评估，单次看便宜，但缺口多时评估成本会挤占 0.50 元预算，反而没钱真正造或装。检索上限设得松与紧都是猜的，没有实测数据。
7. 分流判据难以量化。四条分支多了一次分流判断，就多了一个出错点：该采用的去自造是浪费，该自造的硬套现成是埋雷。分流判据里的定性词（如「匹配高」）没有量化，执行时可能全凭模型感觉。

问题 1：管线位置对不对
结论：插在「缺口报告之后、蓝图之前」是正确的位置，不建议并入需求挖矿，也不建议放在写蓝图时顺带完成。
理由与代价：若并入需求挖矿，会给还没排上队的低优缺口白白花掉检索 token，违背 0.50 元预算约束；若放在写蓝图时顺带完成，模型一旦进入写蓝图模式会有强烈的自造惯性，且无法针对 A 路彻底跳过蓝图。放在「缺口出队进入夜间窗口后、生成蓝图前」作为前置闸门最合理，只对真正排到要做的缺口花检索成本，开发量仅增一个前置检索模块与候选摘要，比蓝图写完再推翻更省钱、出错率更低。代价是 B/C/D 路会多一步串行检索耗时，但受轮次上限控制。

问题 2：检索顺序与停机条件
结论：第 3.2 节「自家 → GitHub → 包生态 → 其他平台」的顺序基本合理，但第零层必须强制全查，第一/二层应按缺口语言生态动态调整先后，且「命中即停」需加防误停条件。
理由与代价：第零层（注册表、wiki、隔离记录）是本地零网络成本，必须硬前置以防重造或找回已隔离工具。当缺口明确是某语言的轻量库/子功能（如 Python/Go 某格式解析）时，应先查 PyPI/Go pkg 等官方包生态看版本、依赖与许可证，再回 GitHub 看源码与 issue，比直接在 GitHub 搜 demo 仓库更准。「命中即停」不能见到第一个高星就停，建议改为「当前层粗筛满 3–5 个候选且至少有 1 个过红线并覆盖 ≥80% 功能才停，否则继续下一层」。代价是少数情况多查一层（多几百 token），但大幅降低假阳性漏选。

问题 3：GitHub 粗筛信号的权重
结论：仅靠主观权重排序不可靠，建议采用「硬性淘汰门槛 + 时效优先排序」：先用硬门槛剔除僵尸库，再按「维护新鲜度 > 文档/发布完整度 > 星数」排序。
理由与代价：建议硬性门槛（估算，需上线后用检索日志校准）：1. 无明确 LICENSE 文件或仓库标明 Archived/Deprecated 直接淘汰；2. 最近提交或发布距今 >18 个月原则上淘汰或降为 C 路借鉴（除非是极稳定的纯算法/规范小工具且 issue 无未解决崩溃）。排序时星数仅作初筛下限（如 >50 星过滤个人玩具库），把「近 6 个月有实质代码提交或 Release + Issue 有维护者回应」排在「高星但两年未更新」前面。代价是可能误杀极少数写完即完美的冷门库，但对 007 而言转走自造远比引入无人维护的坑安全。

问题 4：四分支判据能否落地
结论：第 3.4 节四分支的定性描述（如“匹配高”“接近重写”）由 flash 直接执行会全凭感觉，必须改为可检查的硬清单（并建议合并分支，见问题 12）。
理由与代价：可检查清单建议——走采用/包装必须同时满足：1. 能在 1 条 CLI 命令或 ≤50 行包装脚本内完成目标动作；2. 无需常驻进程或独立数据库；3. 测试机 4 核 4GB 可直接运行其依赖且不引入新重型运行时；4. 5 条红线全过。「包装成本接近重写」的客观判据：若包装胶水代码估算超过 ~100 行、或需魔改上游非公开接口、或需为小功能单独装一套新语言运行时，直接转自造。

问题 5：许可红线细化
结论：第 3.5 节第 1 条原则正确但不够细；必须按「独立外部进程调用」与「源码并入 007 公开库」严格区分，并检查子目录与包清单的多协议冲突。
理由与代价：可执行口径（通用开源协议边界，个案涉商业分发仍需用户确认）：
MIT / BSD-2-Clause / BSD-3-Clause / Apache-2.0 / ISC / Unlicense：采用/包装与借鉴改写源码均放行（Apache-2.0 保留 NOTICE）。
LGPL-2.1 / LGPL-3.0 / MPL-2.0：仅允许作为未修改的独立外部工具通过进程调用；禁止直接复制修改其源码并入 007 Go 核心本体。
GPL-2.0 / GPL-3.0 / AGPL-3.0（强传染性）：禁止代码并入 007 公开库；鉴于 007 有公开库，建议默认禁止进入采用/包装（仅可借鉴公开思路），除非用户特批仅私有自用且严格隔离不随公开库分发。
无许可证（No License）或仅限非商用（NC）：全路红线淘汰。
公开库 vs 私有库：凡并入 007 源码的（C 路代码借鉴）必须全按最严公开库口径；采用前必查根目录 LICENSE、NOTICE 及 package.json/pyproject.toml/go.mod 的 license 字段，多协议冲突按最严条款处理。

问题 6：外部工具的安全审查深度
结论：在无沙箱且 0.50 元预算下不能做全量源码审计，必须用「三阶轻量静态检查 + staging 断网试跑 + 风险分级」来控制成本与风险。
理由与代价：最低必查深度（所有外部采用/包装）：1. 必查安装文件与入口（install.sh、setup.py/pyproject.toml、package.json 的 postinstall 钩子及主入口），用规则+flash 扫描是否含 curl|bash、可疑外连或读取 ~/.ssh、~/.aws、全量环境变量上传；2. 对离线本地工具在 staging 中强制断网试跑，暴露隐蔽外连。分级深度：低风险走上述扫描+断网试跑；中风险额外列出全部目标域名且试用期输出摘要过监工；高风险直接挂起交由鑫鑫或 Muse 人工审代码后放行。待核实：文档未说明 4 核 4GB 测试机当前是否具备轻量级断网测试能力（如 unshare 或代理环境变量置空等隔离手段的实测可用性）。

问题 7：检索成本上限与限流
结论：第 3.6 节候选粗筛 ≤5、细看 ≤3、轮次 ≤2 的上限合理，但需增加单次检索子预算上限（≤0.10 元）与单日检索总占比上限（≤0.20 元），且 GitHub 限流时不死等。
理由与代价：按交互-21 口径（常规锻造 0.05–0.15 元），若检索花超 0.10 元就失去省钱意义，设子上限可防评估反噬 0.50 元每日预算。待核实：文档未说明 007 当前是否已配置只读 GitHub Token。若触发未登录限流（403/429），不要降速死等（会耗尽夜间窗口与 900 秒超时），改为记录 RATE_LIMITED 并转查第二层包生态，若无果则顺延至次日窗口（连续 2 天限流再转 D 路兜底）。

问题 8：分流要不要单独过监工
结论：不需要单独设一道「分流评审门」，随蓝图（B/C/D 路）或验证结果（A 路）由监工一并复核即可。
理由与代价：单独设门会增加 1 次完整上下文加载与监工调用成本；而分流错误在后续阶段天然会被拦截（误选 D 路看蓝图 reuse_search 留痕即被打回，误选 A/B 路会在 staging 失败）。只需把「核查 reuse_search 分流是否合理」设为监工审蓝图/验证结果的固定第 1 检查项即可。

问题 9：采用的工具要不要同等门禁
结论：必须完整走 V1 的风险分级、试用期与熔断，绝不能简化。
理由与代价：正面回应第 2 节硬约束：现成工具不代表适配 007、不代表不会在 4 核 4GB 机器内存溢出、更不代表无安全隐患。若对 A 路放宽门禁（如免试用期或免高风险人工确认），flash 模型很快会倾向于随便找外部工具走 A 路来绕过蓝图与监工，制造严重的逆向激励。四条路在注册门禁、10 次/14 天试用期与连续 2 次失败熔断上必须完全同等。

问题 10：与学习回路共用检索
结论：共用底层抓取器与留痕存储，但保持上层评估与出口逻辑分开；结合第 24 步尚未开工，先做锻造前置的复用检索，第 24 步直接复用其底层检索器。
理由与代价：底层搜索、限流与缓存逻辑完全共通，没必要建两套爬虫；但上层目标截然不同（复用检索是带严苛红线的工具选型，夜学是跨文档综合知识成技能草稿），强行合并上层会让提示词臃肿。先在第 23 步把检索器抽成独立模块，第 24 步开工时直接换评估模板复用即可。

问题 11：验收怎么设
结论：除第 3.8 节顺风局验收外，第一段必须补充「带坑候选拦截验收」和「第零层自家命中截断验收」。
理由与代价：完整验收应包含四类用例：1. 顺风局（已有成熟 MIT 工具，验证选采用/包装不自造）；2. 带坑局（构造或指定一个高星但 3 年未更新+无 LICENSE/含可疑安装脚本的候选，验证评估能按第 3.5 节红线淘汰并转自造，且不把坑工具拉进 staging）；3. 自家命中局（第零层已有工具或已隔离记录，验证不外搜）；4. 失败注入局（沿用 V1，验证连续 2 次失败熔断隔离生效）。

问题 12：有没有更简的做法
结论：有——将「四分支 + 8 维度打分」压扁为「二分支（采用/包装 vs 自造）+ 5 红线 3 硬门槛一票否决」，开发量可再砍约 40% 且更稳。
理由与代价：
合并 A/B 为「采用/包装」：现实中外部工具接入 v1.7 注册表几乎都需要参数映射或薄适配，统一走「适配/包装说明 → staging ≥3 用例验证 → 监工审结果 → 注册」。
合并 C/D 为「自造」：是否借鉴思路只是蓝图 reuse_search 字段有无参考链接的区别，无需两条分支状态机。
砍掉 8 维度打分：过 5 条红线 + 3 条硬门槛（≤50 行适配、无常驻进程、4 核 4GB 可装）就采用/包装，否则直接自造。
损失：仅损失了 inspired 与 forged 的细粒度标签区分及多合格候选间的精细横向打分排序（改为取首个全过且最活跃的候选），但大幅降低了 flash 判错率与代码复杂度。
A.3 修订建议清单（只写改动）
第 3.1 / 3.4 节｜原设计：分流为 A/B/C/D 四条分支，用 8 维度打分与定性词汇判定｜建议改成：第一版压扁为「采用/包装（合并 A/B）」与「自造（合并 C/D，蓝图附参考链接）」二分支；用「5 条红线 + 3 条硬门槛」替代 8 维度打分｜理由：消除分支边界模糊导致的 flash 判错率，降低状态机与提示词复杂度。
第 3.2 节｜原设计：固定顺序「自家 → GitHub → 包生态 → 其他」，命中即停｜建议改成：第零层强制全查；外部层按语言生态动态决定先查 GitHub 还是包生态；单层需粗筛 3–5 个候选且至少 1 个过红线并覆盖 ≥80% 功能才停｜理由：防止在 GitHub 搜到半残高星库就过早停机。
第 3.2.1 / 3.3 节｜原设计：星数只作发现信号，具体权重待定｜建议改成：设硬门槛（无 LICENSE 或 Archived 直接淘汰；距今 >18 个月无提交/发布原则上淘汰或降为参考），按「近 6 个月活跃 + Issue 有响应 > 文档完整 > 星数」排序｜理由：防止 flash 被高星僵尸库误导。
第 3.5 节｜原设计：第 1 条仅笼统写“强传染性许可证不得并入 007 本体”｜建议改成：细化协议口径——MIT/BSD/Apache-2.0 全路放行；LGPL/MPL 仅限独立进程调用、禁抄源码进 Go 本体；GPL/AGPL 默认禁止进入采用/自造代码；无许可证淘汰；必查根 LICENSE、NOTICE 与包清单多协议冲突｜理由：堵住 007 公开库的合规风险，给模型可执行白名单。
第 3.3 / 3.5 节（安全审查）｜原设计：无明确的外部工具静态检查与断网验证要求｜建议改成：采用/包装前必查安装脚本/钩子（防 curl|bash 与异常外连），离线类工具在 staging 强制断网试跑；高风险外部工具人工审代码放行｜理由：无沙箱下用低成本硬检查拦截隐蔽恶意行为。
第 3.6 节｜原设计：仅设候选数与轮次上限，限流处理待定｜建议改成：增设单次检索子预算上限（≤0.10 元）与单日检索总占比上限（≤0.20 元）；触发 GitHub 限流不死等，转查包生态或记 RATE_LIMITED 顺延次日（连续 2 天限流转自造）｜理由：防止评估成本反噬每日预算，避免夜间窗口超时卡死。
第 3.8 节｜原设计：复用验收只测顺风局选 A/B 路｜建议改成：补充「带坑候选（无许可/僵尸库/异常安装脚本）拦截验收」与「第零层自家命中截断验收」｜理由：确保系统既能找对工具，更能把坑货挡在门外。
A.4 异议与依据
第 3.5 节第 4 条（依赖膨胀缺少硬约束）：第 4 节第 3 条已自曝外部工具可能导致“tools 目录变杂物间、依赖膨胀侵蚀 Go 单体”，但第 3.3/3.5 节仅用“依赖不重”定性描述。依据第 2 节硬约束（4 核 4GB 共存代理服务、Go 单体+脚本），应明确禁止为单个工具引入测试机原本没有的重型语言运行时或独立包管理器环境。待核实：文档未给出当前 4 核 4GB 测试机已预装的运行时清单及剩余磁盘/常驻内存余量（缺测试机基线数据）。
第 3.1 / 3.6 节（未设上游断裂最小监测闭环）：第 4 节第 5 条自曝没有“上游变化监测”，第 3.8 节未将其接入现有定时机制。其实只需规定外部工具一律锁定版本号或 Commit Hash 安装（禁拉 latest/main），并在第 20 步每周自查或工具连续失败熔断时顺带检查一次上游状态即可。
A.5 必须由鑫鑫本人拍板的事项
外部工具 GPL/AGPL 强传染性协议的红线口径（对应第 5 节问题 5）：选项 A 为保守口径——因 007 有公开库，GPL/AGPL 工具默认一刀切禁止采用与抄代码，只用 MIT/BSD/Apache-2.0 等宽松协议；选项 B 为宽松口径——仅禁抄代码进 Go 公开库，允许在私有服务器以独立 CLI 进程调用 GPL 工具并标明不随公开库分发。代价对比：选 A 会错失部分好用的 GPL CLI 工具；选 B 需在未来整理公开库分发时严格人工剥离，稍有疏忽有合规争议。推荐选 A。
是否采纳「二分支 + 红线硬门槛」简化版替代「四分支 + 8 维度打分」（对应第 5 节问题 12）：选项 A 为先上二分支简化版跑通复用流程；选项 B 为按第 3 节完整四分支 + 8 维度评估落地。代价对比：选 A 省掉约 40% 分流复杂度且降低 flash 判错率，仅少了一点统计标签细分；选 B 分类更细但开发更重且缺校准数据。推荐选 A。
是否为 007 配置一个纯公开只读 GitHub Token（对应第 3.6 节限流提醒）：选项 A 为配置一个仅公开仓库只读、无任何写或私有库权限的 GitHub Token；选项 B 为不配 Token 纯匿名搜索，撞限流就顺延。代价对比：选 A 需花 1 分钟建一个无权限纯读 Token（无沙箱泄露也仅有公开只读风险）；选 B 零配置但夜间集中检索更易撞限流。推荐选 A。
A.6 与 Muse 方案最大的一个分歧
最大分歧：分流架构与评估复杂度——Muse 方案设计了「四分支（A/B/C/D）+ 8 维度打分」的精细评估流，而我主张第一版压扁为「二分支（采用/包装 vs 自造）+ 5 红线 3 硬门槛一票否决」。
为什么我认为我是对的：第 3.4 节明确执行分流判定的是快速模型（flash），且第 4 节第 7 条 Muse 也已自曝「定性词没有量化，执行时可能全凭模型感觉」。在缺乏历史真实检索样本校准的情况下，让快速模型同时对 8 个维度打分、还要精确区分“A 直接采用 vs B 薄包装”“C 借鉴重造 vs D 从零造”，极易产生分流误判与无效返工。
如果按 Muse 的方案做最坏会发生什么：flash 在四分支边界反复横跳（如把需要参数适配的工具硬塞进 A 路导致 staging 失败，或在 8 维打分上消耗过多 token 挤压 0.50 元每日预算），最终导致复用环节变得比直接自造还慢、还贵，重演“设计很完整但实际不好用”的弯路。
